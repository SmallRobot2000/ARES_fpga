# 512x384 conversion validation

The source framebuffer is 512x384 RGB565, scaled 5:4 to the unchanged
640x480 VGA timing. The RTL and software use LG15 (six 64-row strips), one TMU,
depth/stencil/fog enabled, mipmapping/filtering disabled. Autoload stays off.
The existing physical reservations and 21 DMA-proxy buffers are unchanged.

The external RasterIX ceiling-division change and compile-time tests are
preserved in `patches/0001-correct-strip-ceiling.patch`. The dispatcher already
uses ceiling division for its runtime strip count. Its equal-height strip
handling gives exactly six 64-row strips here; no partial final strip occurs.
Its existing handling of other resolutions whose heights do not divide evenly
by the runtime strip count was not changed by this conversion.

## Local checks

- `python3 linux/rasterix/tests/check-hardware-config.py`
- `sh linux/rasterix/tests/check-triangle-lists.sh` (fresh native CMake build)
- `sh linux/dma-proxy/tests/check-framebuffer-handshake-rtl.sh`
- `sh linux/dma-proxy/tests/check-framebuffer-scaler-rtl.sh`
- `sh linux/dma-proxy/tests/check-display-command-rtl.sh`
- `python3 linux/dma-proxy/tests/check-framebuffer-reservation.py`
- `python3 linux/dma-proxy/tests/check-texture-reservation.py`

The scaler test compares every active pixel against an independent coordinate
pattern through the synchronous line-buffer model. It checks all 512 columns
and 384 rows, exactly four sequential 16-beat bursts per source row, the full
1536-burst frame count, address bounds, no traffic before a valid framebuffer,
and immediate/VSync handshakes. AXI stalls include a burst held across VSync
a new immediate swap coinciding with replacement-line completion, and a
VSync request arriving exactly at the vertical-blank boundary. The
displayed complete buffer must never be overwritten during a refill.

The native capture validates 30 lists for setup, three frames, and teardown,
64-row strip resolution, 36 Y-offset writes, full 32768-pixel strip operations,
and four full-frame `0x23000094` swaps (including teardown). Compile-time tests
cover one strip, six exact strips, and a partial seventh strip.

Native and RV32 builds were configured independently under
`/tmp/ares-512-work/native` and `/tmp/ares-512-work/rv32`. The device tree compiles
without warnings. The existing checked-in-workspace DTB was stale: unlike the
DTS, it lacked texture and auxiliary reservations. Use the rebuilt DTB below.

## Files for the board

Output directory: `linux/rasterix/artifacts/512x384/`.

- `ares-gl-triangle`, `ares-gl-animate`, `proxy-smoke`: static RV32 Linux
  executables. Copy them to `/root/` (or another executable location).
- `tree-rasterix-display.dtb`: install as the boot medium's `tree.dtb` and reboot.
  It reserves textures, both framebuffer slots, auxiliary memory, and scratch.
- FPGA image: generated by the user in Vivado after refreshing the modules
  and rebuilding synthesis/implementation. The expected output is
  `ARES_fpga.runs/impl_1/Block_top_wrapper.bit`. Timing and hardware validation
  remain pending; no new bitstream is included in this bundle.

The FPGA build uses a copied project at `/tmp/ares-512-work/fpga`, retaining
existing user edits without resetting the original project's synthesis or
implementation runs. Its script/log/reports are in `/tmp/ares-512-work/`.
The user elected to run implementation/bitstream generation in Vivado. A stop
request was placed on the isolated implementation, effective at its next step
boundary. Full synthesis passed before the final boundary-handshake correction;
the final scanner also passed standalone Vivado 2025.2 synthesis. Reports are
in the bundle’s `reports/` directory. Automated checks listed above all passed.

In Vivado's Tcl Console, with the original project open:

```tcl
source /home/lovro/ARES/ARES_fpga/ARES_fpga/linux/rasterix/tests/refresh-framebuffer-module.tcl
reset_run synth_1
launch_runs impl_1 -to_step write_bitstream -jobs 4
```

This launches required synthesis dependencies before implementation. Check the
routed timing summary and DRC before programming. If using the GUI instead,
refresh modules, reset/run synthesis, run implementation, then generate the
bitstream. Use matching `.ltx` probes if your build enables ILA debugging.

## Hardware checks (user performs these)

After programming the matching image and booting the rebuilt device tree:

```sh
chmod +x /root/proxy-smoke /root/ares-gl-triangle /root/ares-gl-animate
grep -E '97800000|97c00000|97e00000|97f00000' /proc/iomem
grep xilinx-dma /proc/interrupts
/root/proxy-smoke --display
/root/ares-gl-triangle
/root/ares-gl-animate --frames 300
grep xilinx-dma /proc/interrupts
dmesg | tail -60
```

Check full-screen bars and the one-source-pixel grid for the 0,0,1,2,3,4,4,...
repeat cadence on both axes. During animation, exercise CompactFlash and
Ethernet and check for DMA errors or stalls. Visual scaling, stable swaps,
and CF/Ethernet regression checks remain hardware acceptance criteria.
